## Проверенные контракты

- Domain: календарь, точность now, 09:00–18:00, 30–120 минут, произвольные
  минуты, полуоткрытые интервалы, собственный id и целевая дата.
- HTTP/repository: DTO как unknown, PATCH с актуальной записью, sync read/check/write,
  ошибки Storage без успеха/сброса, исторические данные, реальные конкурентные POST.
- Application: один date/key/payload, независимый draft, abort старого GET,
  отсутствие повторов мутации/optimistic updates, актуальный Clock при отправке.
- Успех create/update/delete + failed GET: mutation cache остаётся success,
  очищается сохранённый draft, повтор отправляет только GET.
- Настоящий устаревший POST/PATCH → 409: конкурента создаёт обычный HTTP handler;
  форма сохраняется, список обновляется, исправление позволяет сохранить.
- Invalidate: активный день обновляется; неактивный только становится stale.
  Paused refetch показан отдельно от успеха записи и продолжает только GET при online.
- Bootstrap: ждёт worker; ошибка регистрации не возвращает API и допускает повтор;
  real не запускает MSW; некорректная конфигурация отвергается.
- Поиск импортов подтвердил отсутствие MSW/repository/localStorage в UI,
  application, API client и domain. DI-контейнер и дополнительные слои не добавлены.
- M1–M5 были новыми файлами в изначально пустой папке. Чужие данные не сбрасывались;
  удалялись только созданные при проверках записи. Секреты, зависимости и dist
  исключены из Git; публикация и push не выполнялись.

## Major: потеря активации MSW 3.0.3 в открытой вкладке

**Доказательство:** production preview с неизменным bundle; активная SW-регистрация,
но GET `/api/bookings` через несколько минут вернул `text/html` от Vite.
Диагностический MOCK_ACTIVATE без перезагрузки сразу вернул JSON на том же GET.
Это локализует потерю состояния активации worker, а не ошибку repository/Query.

В штатном worker 3.0.3 обработчики MOCK_ACTIVATE/KEEPALIVE_REQUEST/INTEGRITY_CHECK
используют `event.waitUntil(await sendToClient(...))`, но эти уведомления не получают
ответа от клиента. Новые VM-тесты фактического worker показывают незавершающиеся
lifetime-promises: **3/3 упали** на файле из коммита M5. Это согласуется с остановкой
worker по browser lifetime limit; само событие termination через CDP не записывалось.

**Минимальное исправление:** точная фиксация MSW **2.15.0**, его стандартный
`onUnhandledRequest` и регенерация worker штатным CLI. Сгенерированный файл
побайтово равен файлу из установленного пакета: ручных изменений vendor-кода нет.
Стек, бизнес-логика, HTTP-контракт и разделение слоёв не менялись. В версии 2 Promise уведомления не включён в waitUntil, поэтому lifetime
обработчика не остаётся открытым.

**Локальная регрессия:** 116 тестов в 8 файлах, включая 3 worker-lifetime проверки,
прошли на 2.15.0; typecheck/lint и обычная/demo сборки проходят. Повторная чистая
установка по новому lockfile прошла (295 пакетов). Во время установки из registry
npm audit сообщил 0 уязвимостей на момент запуска; это не отдельный security audit.

**Браузер на исправленной версии:** worker 2.15.0 запущен в production preview
в 08:01:52 UTC; спустя **393 секунды** без reload/ручной реактивации GET вернул
200 application/json. Затем конкурентный POST → 201, устаревшая форма → настоящий
409, список обновился, все поля сохранились; исправление → 201. Это локальное
доказательство воспроизведённого сценария, не длительный нагрузочный тест.
Подтверждение удаления оставалось открытым около минуты: DELETE выполнился,
следующий GET остался JSON. После reload сохранённая конкурентная запись
отобразилась, PATCH через форму и DELETE прошли. Итоговый GET на тестовую дату
вернул пустой массив; после reload в консоли 0 ошибок и 0 предупреждений.

## Повторный implementation review после локальной сдачи M6

  Storage-формат и миграции не менялись; дополнительных зависимостей нет.
- После исправления: 118 тестов / 8 файлов, typecheck, lint, обе сборки
  (обычная/demo), git diff --check — exit 0. Браузер и два TZ в этом проходе
  повторно не запускались: соответствующие предыдущие доказательства выше.
- Входное рабочее дерево было чистым; изменены только клиент, регрессионные

- M6 остаётся локально подготовленным: Git remote, размещение, внешние ссылки

## Выбор времени после замечаний по записи экрана

На приложенной записи нативный Chromium time picker использует AM/PM, меняет
выбранное значение при прокрутке колонок и показывает часы вне рабочего дня.
Атрибуты min/max задавали валидацию, но не ограничивали нативные варианты.
Заменён только ввод времени: ЧЧ:ММ с минутным списком, прямым вводом и
подтверждением кликом/Enter. Прокрутка, стрелки и Escape не меняют черновик
до подтверждения. Четыре цифры нормализуются (0917 → 09:17).
Начало: startMin из controller — 17:30; окончание: 09:30–18:00.
Список ограничивает рабочие часы; пересечения и длительность по-прежнему
независимо проверяются domain и mock API при сохранении.

Критический review выполнен самостоятельным повторным чтением TimeField и
его интеграции с controller/form. Фокус серверных ошибок по прежним id сохранён,
занятость блокирует оба элемента, raw-invalid ввод проверяется существующими
правилами. При открытии/клавиатурной навигации меняется scrollTop самого списка,
без scrollIntoView страницы. Новых зависимостей и изменений хранилища нет.

Фактически выполнены npm run typecheck, npm run lint, npm run test:run
(124 теста / 9 файлов), npm run build, npm run build -- --mode demo — exit 0.
Шесть новых тестов: минутные диапазоны, отсутствие AM/PM, прокрутка без записи,
явный выбор, цифровой ввод, клавиатура/Escape/blur и отсутствие доступных стартов.
Production preview 127.0.0.1:4173: прокрутка списка изменила только его scrollTop
(до 5765), оставив start=14:17, end=15:17 и scrollY=222; границы окончания
09:30 и 18:00. ArrowDown/Enter выбрал 15:18 и закрыл список; Escape также закрывает.
При viewport 320 px documentWidth=320, список помещается по ширине.
В браузере записи не создавались; проверена локальная demo-сборка, публикации нет.
